# The path to v0.3.0

The goal: give the pipeline a collection, leave it running, and afterwards know
what happened to every capture. [ROADMAP.md](../ROADMAP.md) owns acceptance
criteria and release gates; this document orders the work. Live task state stays
in the maintainer's tracker. No dates or completion percentages are implied.

## What the version means

`0.3.0-alpha.1`, `0.3.0-alpha.14` and subsequent alphas are prereleases
of `0.3.0`. Higher alpha numbers identify later previews, not distance to
completion. The intended progression is:

**alpha previews -> beta testing -> v0.3.0 release**

Only the release gates in ROADMAP decide when to advance. Feature commits do
not consume version numbers; finished, tested groups of changes become releases.

## Ordered implementation and verification

| Step | Deliverable | Evidence needed before moving on |
|---|---|---|
| 1. Establish the record foundation | Extend alpha.11 catalog job records as the authoritative invocation outcome model, as approved in ROADMAP. Use the gap assessment below to scope implementation. | Preserve existing job IDs and evidence links; define additive fields or a versioned migration and check consumer compatibility before changing the schema. |
| 2. Make every attempt observable | Complete incremental records, including early failures, the furthest completed milestone, resolved settings, tool versions, timings and artifacts. | Tests for success, config/prerequisite failure, stage failure and interruption; the surviving record explains how far each attempt got. |
| 3. Guard the GPU | Prevent independent pipeline invocations from silently competing for the same GPU. | A second invocation refuses clearly; termination does not leave a permanent stale lock. |
| 4. Run a collection | Discover canonical captures and derive each run from one base configuration; execute sequentially and report failures without losing the remaining captures. | Multi-capture fixtures prove discovery, overrides, deterministic ordering and failure handling; input photographs remain unchanged. |
| 5. Resume safely | Identify verified completed work and skip it when a partly failed batch is rerun. | A rerun preserves successful outputs and avoids duplicate successful runs; incomplete or invalid outputs are not mistaken for completion. Define behavior for changed inputs/settings explicitly. |
| 6. Summarize from records | Provide the rebuildable catalog index and catalog batch provenance linking all attempts. | Deleting and rebuilding the index preserves the same answers; batch membership and each failure remain traceable to authoritative records. |
| 7. Prove the collection promise | Exercise the full documented route on a real collection, including a controlled failure and rerun. | For every capture: success/failure, elapsed time, output artifacts and failure milestone are recoverable. Successful captures are skipped on rerun. All ROADMAP v0.3.0 criteria have evidence. |
| 8. Publish beta and test independently | Cut the first beta after step 7. Have someone other than the author follow the docs, then fix blockers and repeat affected checks. | Recorded independent installation and collection-run results; documentation is sufficient without private workspace knowledge. |
| 9. Release v0.3.0 | Review acceptance evidence, run the required suites, finish documentation and publish a deliberate release commit and annotated tag. | All v0.3.0 acceptance criteria pass; release validation is complete. Follow ROADMAP's release-time versioning rule. |

Steps describe a recommended sequence, not a second task dependency database.
Record reconciliation comes first because completion checks and summaries need
an agreed authoritative record. GPU protection must exist before unattended real
batch trials. Unit fixtures can be developed before spending GPU time.

## Scope boundaries

Native Windows support belongs to the later v0.4.0 milestone. Linux under WSL2
is the existing route on Windows hosts. A plant representation choice, a second
species asset and biological validation remain separate work; none substitutes
for the collection acceptance test. Existing experimental analysis tools can
remain explicitly experimental in a v0.3.0 reconstruction release.

## Catalog gap assessment

Code inspected 2026-10-20: `pipeline/plant_catalog.py`, class `CatalogJob`;
`pipeline/run_pipeline.py`, functions `main`, `run_pipeline` and
`run_command`. This is a code-inspection baseline, not a runtime acceptance
result. Recheck it against the implementation before marking criteria complete.

| Criterion | Existing foundation | Work still owed |
|---|---|---|
| Durable invocation record | `CatalogJob.write/save` atomically replace JSON; artifact/evidence links also save the job. | Make the required record available for ordinary collection runs; emission is currently opt-in. |
| Failed attempts | `main` finalizes stage failures and handled keyboard interruptions. | Configuration loading returns before catalog creation. Define pre-capture/invalid-config attempt identity without inventing a capture. Hard termination can leave running state; preserve it as incomplete until explicitly reconciled. |
| Furthest verified milestone | Stage output artifacts are linked. | Add structured milestones and timestamps at verified boundaries. A linked directory alone is not the complete milestone ladder. |
| Reproducibility | Original INI, selected images, repository commit/version, machine, frozen config and command log. | Record resolved runtime settings (including generated run ID and effective downscale), dependency versions and structured per-stage timings. |
| Queryable summary | Job JSON is available to catalog consumers. | Implement the rebuildable index from authoritative job records. |
| Batch provenance | Individual jobs have stable invocation IDs. | Define and implement batch membership and attempts without copying job outcome state. |
| Verification | Writer and runner integration were inspected. | Establish dedicated producer/integration tests for success, early failure, stage failure, interruption, atomic updates and compatibility. No catalog-specific tests were found under `pipeline/tests` in this inspection. |

## First implementation task

Specify the catalog job extensions and early-failure representation against the
existing producer and consumer contracts. Then implement step 2 with dedicated
tests. Preserve existing records and Mission Control reads; do not create a
second authoritative run-record store.

## Invocation progress implementation

[The producer contract](../pipeline/CATALOG-RECORDS.md) describes implemented
progress fields, early-failure requirements and tests. The gap table above is
the pre-implementation inspection baseline, not a current implementation claim.
Real reconstruction acceptance, unknown-capture attempts, automatic enablement,
indexing and batch provenance remain outside this increment.
